# Liquid Labs - Post Cache API

This RESTful Web API is built with ASP.NET Core. It fetches blog post data from a public third-party API (JSONPlaceholder) and stores it locally in Microsoft SQL Server to serve as a local cache. Because subsequent requests for the same data are fulfilled directly from the local database, it minimizes unnecessary external API calls.

This application acts as a proxy and caching layer between the client and the JSONPlaceholder API. When a client requests 'posts', the system first checks the local SQL Server database. If the requested data exists locally, it is returned immediately. If the data is not present, it is fetched from the JSONPlaceholder API, stored in the local database, and then returned to the client.

## Features

*   Retrieve all posts from the local database or an external API.
*   Retrieve a single post by ID; automatically falls back to the external API if the post is not found in the cache.
*   'Read-through' caching mechanism implemented using MS SQL Server.
*   Direct SQL data access using `Microsoft.Data.SqlClient` (no ORM used).
*   Global exception handling middleware to maintain a clean API response structure.
*   OpenAPI / Swagger integration for easy API exploration and testing.

## Architecture

This project follows a clean layered architecture that separates API controllers, business logic, data persistence, and external HTTP integrations.

*   **PostsController:** Handles HTTP requests and delegates operations to the service layer.
*   **PostService:** Contains core caching logic and coordinates between the repository and the external API client.
*   **PostRepository:** Manages direct SQL queries and data storage operations.
*   **JsonPlaceholderClient:** A 'Typed HttpClient' wrapper for communicating with the JSONPlaceholder API.
*   **ExceptionMiddleware:** A centralized exception-handling mechanism designed to detect unhandled errors and provide a consistent 500 error response.

## Why were these technologies chosen?

### ASP.NET Core Web API
This was selected due to its high performance, strong typing system, built-in Dependency Injection (DI) framework, and robust middleware support when creating RESTful APIs using C#.

### Microsoft.Data.SqlClient (Without using an ORM)
In accordance with the assignment requirements, the use of Object-Relational Mappers (ORMs) like Entity Framework Core was excluded. `Microsoft.Data.SqlClient` provides direct and granular control over database connections and command execution through native classes such as `SqlConnection`, `SqlCommand`, and `SqlDataReader`.

### Swagger / OpenAPI
This was integrated via `Swashbuckle.AspNetCore` to facilitate interactive visual documentation and simplified endpoint testing during the development process.

### JSONPlaceholder
This was chosen as a reliable, free public REST API that provides mock post data without requiring complex authentication processes or API keys.

### Dependency Injection (DI)
Built-in DI is used to register repositories, services, and typed HTTP clients. This helps maintain loose coupling between system components, facilitates class testing, and simplifies maintenance.

## Database

* **Database Name:** `PostCacheAPIDB`
* **Table Name:** `PostCache`

### Schema Definition

```sql
create table dbo.PostCache (
	Id int not null primary key,
	UserId int not null,
	Title nvarchar(255) not null,
	Body nvarchar(max) not null,
	CreatedAt datetime2 default sysutcdatetime()
);
```

* Id: The primary key corresponding to the post ID in JSONPlaceholder.
* UserId: The ID number of the user who created the post.
* Title: The text (string) representing the title of the post.
* Body: The main content of the post.
* CreatedAt: The timestamp automatically generated by SQL Server (using SYSUTCDATETIME()) at the time the record is inserted into the cache.

### Database Setup 

1. Open your SQL Server tool (SSMS).
2. Connect to your local SQL Server instance.
3. Open the `Database/schema.sql` file from the repository.
4. Execute the script to create the `PostCacheAPIDB` database and the `PostCache` table.

Update the database connection string in appsettings.json to point to your local SQL Server instance.

```
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=<YOUR_SERVER_NAME>;Database=PostCacheAPIDB;Trusted_Connection=True;TrustServerCertificate=True;"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "AllowedHosts": "*"
}
```
Replace `<YOUR_SERVER_NAME>` with your SQL Server instance name.

### API Endpoints->

1. GET  -  /api/Posts  -  Returns all posts (from DB if available, else fetches from API)
2. GET  -  /api/Posts/{id}  - Returns a single post by ID

### Response Codes

`200 OK` - The request was successful, and the post data was returned.

`400 Bad Request` - Invalid request parameters.

`404 Not Found` - The relevant post ID does not exist in the local database or the external API.

`500 Internal Server Error` - An unexpected error (exception) occurred on the server.

### Caching Process

`GET /api/Posts`

Checks the database for existing records.
If records exist, it immediately returns the cached data.
If the database is empty, it sends a request to GET /posts on JSONPlaceholder.
Inserts (writes) the retrieved items into the SQL database.
Returns the list of data to the client.

`GET /api/Posts/{id}`

Checks the database for the record matching the @Id.
If found, it returns the record from the database.
If not found, it makes a GET /posts/{id} request to JSONPlaceholder.
If the item exists externally, it persists it in SQL Server and returns the result.
If the item does not exist externally, it returns a 404 Not Found response.

 ### Error Handling
 
* **Validation:** Endpoint routes verify input parameters. Inputs such as `id <= 0` immediately trigger a '400 Bad Request' response.
* **Not Found:** If the requested resource ID does not exist in the database or external API, a '404 Not Found' status is returned.
* **Global Exception Middleware:** The `ExceptionMiddleware` catches any unhandled runtime exceptions, logs the error details using `ILogger`, and generates a standard JSON '500 Error' response.

```
{
  "message": "Something went wrong. Please try again later."
}
```
## Testing

The following manual tests were conducted to verify the application's stability.

* **Build Test:** The `dotnet build` command was executed to ensure there were no compilation errors.
* **Initial Endpoint Call (Cache Miss):** A `GET /api/Posts` request was made with an empty database. Data received from the external API was verified, and the `Posts` table was populated (100 rows were inserted).
* **Database Population Test:** The `SELECT COUNT(*) FROM PostCache` command was executed in SQL Server to verify data persistence.
* **Retrieving a Single Record (Cache Hit):** A `GET /api/Posts/5` request was made. A rapid response, served directly from the SQL database, was confirmed.
* **Cache Miss and Synchronization (Sync):** Post ID 5 was manually deleted from the SQL table, and `GET /api/Posts/5` was executed; the retrieval of data from the external source and its re-insertion into SQL Server were then verified. 
* **Invalid input and 404 tests:** It was confirmed that `GET /api/Posts/-1` returns a `400 Bad Request` response and `GET /api/Posts/99999` returns a `404 Not Found` response.

## Deployment

*Note: This application was developed and tested in a local environment. The steps below describe how to publish and deploy the application to a production server.*

### Database Deployment

1. Connect to the target production SQL Server instance.
2. Execute the `Database/schema.sql` script to set up the `PostCacheAPIDB` database and tables.


### API Application Deployment
1. Publish the application binaries
```
dotnet publish -c Release -o ./publish
```
2. Copy the contents of the `./publish` directory to the target hosting environment (Azure App Service).
3. Configure the `ConnectionStrings__DefaultConnection` environment variable on the target host to match the production database credentials.
4. Run the application's executable file, or configure a reverse proxy to point to the API port.

### API Key

* Setting up an API key is not required for this project. JSONPlaceholder is a public testing API that allows requests to be made without API keys or authentication headers.

### ORM / Database Access

* In accordance with project constraints, this application completely avoids the use of ORMs (such as Entity Framework Core, Dapper, etc.).
* All database operations are implemented using raw ADO.NET via Microsoft.Data.SqlClient. To prevent SQL injection risks, parameterized commands (e.g., `WHERE Id = @Id`) are used for all queries instead of inline string concatenation.

### Git Workflow

* The project repository was initialized at the very beginning of the project.
* Progressive commits are implemented sequentially (e.g., initial setup, repository layer, external API client, service logic, middleware, and documentation).
* A clean commit history containing source code and standalone database creation scripts.
